# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Advanced Markdown Export exports a set of notes together with the files they depend on. The user picks what travels in a checkbox tree; the plugin writes the bundle out with its internal links still resolving.

## Architecture

Three layers. The bottom two are headless and unit-testable with no DOM, which is deliberate — the graph rules are where the correctness risk lives.

- `src/dependency-resolver.ts` — one file's **direct** dependencies. Never call it for a node the user has not expanded or ticked; lazy expansion is a hard requirement, not an optimization (a folder root can be thousands of notes). Asserted by a call-counter test in `export-forest.test.ts`.
- `src/export-forest.ts` — the selection model: roots as a set, first-occurrence ownership, repeats as disabled mirrors, tick-driven depth.
- `src/export-writer.ts` — walks the chosen files and rewrites their links. Where the bytes land is behind the `ExportTarget` seam, implemented in `src/export-targets/`.
- `src/export-destination/` — a facade choosing between the desktop directory picker (`window.electron` + `node:fs`) and the in-vault folder used on mobile. The desktop module must never be statically imported: it is reached by a conditional `await import()` gated on `Platform.isDesktopApp`. `isDesktopApp`, not `isDesktop` — the module needs Electron, and that is the flag that says Electron is there, which is also why it needs no `window.electron` presence check of its own.
- `src/modals/` — the tree UI. `obsidian-dev-utils` has no tree component, so this is hand-built on Obsidian's native `tree-item` classes.
- `src/export-flow.desktop.integration.test.ts` — the one test that proves the pieces fit. It mocks only the OS directory dialog and drives the real menu, the real modal DOM and the real writer, then reads the bundle back off disk. It is what caught the bundle being named after a note's *path* rather than its name. Because `exportBundle` writes the chosen files one at a time, anything reading the bundle back must wait on the completion notice, never on a single file appearing — waiting on the first file raced the last one into existence and lost it on roughly one run in six.
- `src/export-flow.android.integration.test.ts` — the same proof on a phone, and the answer to a whole class of defect the other suites are blind to. The mobile destination is reached by a conditional `await import()`, so a module it pulls in can throw as its body loads and take the export down while the plugin still loads perfectly: the Android smoke test stays green, the unit tests never load the real chain because they mock `prompt`, and the desktop suite takes the other branch. That is exactly what shipped in 1.0.0 (the `fflate/browser` note under Deviations). It covers BOTH mobile destinations on purpose — the folder case proves the chain loads, the ZIP case reads the archive back and unzips it in Node to prove `zipSync` actually runs there, because a green folder case says nothing about the compressor it never reaches.
- `src/folder-root-scale.desktop-performance.integration.test.ts` — lazy expansion as a user can see it: a 300-note folder root draws 300 rows and not one more. The fixture notes all embed the same attachment, so an eager-expansion regression shows up as extra rows rather than as a slow test on a slow machine. Building the fixture, opening the root and clearing up are three separate closures: only the middle one is timed, and only it declares any waiting (see *Wait budgets* below).

## Invariants that are easy to break

- **The first occurrence of a file owns its live checkbox.** Every later occurrence — a cycle, a diamond, a folder member reached through a sibling — renders disabled and mirrors the owner's state, including when the owner is *unchecked*. Never let a repeat become the live checkbox: a checkbox that migrates between rows as the user toggles is worse than one that stays put.
- **`maxTraversalDepth` is a traversal cap, not the depth control.** The user's ticks drive depth. The cap only stops unbounded growth.
- **Attachment/note classification drives the default check state**, and that policy is a setting — never hard-code the attachments-on/notes-off rule at a call site.
- **Unchecking a note drops what it pulled in, but only what nothing else still holds.** `pruneOrphanedDescendants` is what makes the tree tell the truth about the export set; without it an unticked note leaves its auto-ticked attachments behind and they ship anyway. Roots are exempt — they are the user's explicit pick.
- **Link rewriting is markdown-only.** Everything else, a canvas included, is copied byte for byte, so a canvas node pointing out of the export keeps its link whatever the dangling-link setting says. Documented in `demo-vault/01 Exporting.md`; rewriting canvas JSON would mean `referenceToFileChange` + `applyFileChanges` rather than `editLinksInContent`.

## The screenshot capture suites

`npm run capture:screenshots` drives the export tree in a real Obsidian and writes `images/screenshots/screenshot-desktop-N.png` (five frames at 1200x800) and `screenshot-mobile-N.png` (five at 900x1600), desktop leg first because both legs share one machine. They are the community-store listing shots and the README gallery.

- The suites are named `*.desktop-capture.` / `*.android-capture.` so they match **none** of the standard project globs. Capturing opens a window and leaves a modal on screen to photograph it, and it rewrites ten committed PNGs — neither is something `npm run test:integration` should ever do.
- **The staged vault is the demo vault's `Example/` graph, read off disk rather than retyped.** The cycle (`B` links back to `A`) and the diamond (`C` embeds an attachment `A` already has) are what produce the greyed, disabled repeat rows, which are the modal's most distinctive behavior and the only part of it a still frame can show. Reading the notes and the four PNGs from `demo-vault/Example/` is what stops the pictures and the documentation drifting apart.
- **`labelScreenshot` scales one line to the frame width and does NOT wrap.** A caption much past ~45 characters at 1200px is clipped mid-word, and nothing fails — the frame just ships with half a sentence burned into it. Found here on the first run: the 73-character `A file already in the bundle is listed once, and mirrored where it repeats` was burned in with its first four and last three characters sheared off, so the frame shipped a caption that began mid-word. The fix is a shorter caption, not a smaller font.
- **`labelScreenshot` needs `sharp`**, an optional peer of `obsidian-integration-testing`. Without it every frame fails at the caption step with `Cannot find package 'sharp'` — *after* the capture itself succeeded, so the failure looks unrelated to what actually went wrong.
- **The band is composited over the BOTTOM of the frame**, which on desktop is Obsidian's status bar and on a phone is the modal's own footer. Do not caption a mobile frame with something only the footer could prove.
- **No destination-prompt shot yet, but the obstacle is gone.** The mobile set's fifth frame was meant to be the `Where should the export go?` prompt — the one screen with no desktop equivalent, since a phone has no system directory picker. It could not be captured, because on a device the export threw inside `createExportDestination` before the prompt opened; the slot mirrors the desktop toolbar frame instead. **That defect is fixed** (the `fflate/browser` note under Deviations), and `src/export-flow.android.integration.test.ts` now drives that prompt open on a device and answers it — so the sequence to copy exists and the frame is merely un-taken. Replacing the duplicated fifth frame needs an explicit `capture:screenshots` run on the `obsidian_screenshots` AVD, so it is its own piece of work rather than something to fold into an unrelated change.
- **No settings-tab shot, by storyboard choice.** Owner's call for the fifth slot, and the rule behind it: a screenshot has to demonstrate the plugin's usefulness, so settings earn at most one slot and only where the settings themselves are the feature. Here the tree modal is the product. **This is not a capability limit, and it no longer costs a recipe** — Obsidian ships `settingsPopoutWindow` as `true` (1.13.7 and 1.14 alike), and the popout reassigns `activeWindow`, so `app.setting` would land in a second Electron window and never reach the captured document; but `obsidian-integration-testing` writes that default off into every vault it owns, beside the `alwaysUpdateLinks` it already wrote, since 12.1.0 — which is this repo's floor. So a settings frame here needs no `setConfig` of its own: `open()` attaches `containerEl` itself on a harness-owned vault. Do not read the harness's own pre-attach in `openSettingsTab` as dead code — it is kept deliberately, because a vault built in-worker carries no default and removing it turns two of its assertions red. Established on 2026-09-03, the same day this suite was written — the earlier reading of that failure as an Obsidian 1.14 regression was wrong — and moved into the harness on 2026-09-05.
- **The mobile leg runs on the `obsidian_screenshots` AVD**, 900x1600 at density 320 — exactly the size the store asks for, so no crop or rescale. The shared `obsidian_test` AVD cannot stand in: it is 1344x2992, and resizing it at runtime recreates the activity and with it the WebView the session is attached to. The mobile leg also drops `baseFontSize` to 13 (`app.updateFontSize()` is what re-renders) because the AVD is a 450x800 dp screen and the deeper trees do not otherwise fit.
- **The gallery's `blob/HEAD` anchors 404 in `lint:md` until the branch is merged**, because `HEAD` resolves against the default branch. That is expected on the branch; re-run `lint:md` after the push.
- **Do not pre-boot an emulator** and check `Get-Process | Where-Object { $_.ProcessName -like 'qemu*' }` is empty before starting the Android leg. A hand-started device is not adopted, and a collision leaves a zombie `qemu-system-x86_64-headless` holding the AVD's `multiinstance.lock` that poisons every later run.
- **Killing an Android capture run ORPHANS its emulator, and the orphan must be swept, not left alone.** The kill takes the `emulator` wrapper and leaves the `qemu-system-x86_64-headless` backend alive holding TCP 5554/5555 — so `adb devices` still lists a healthy-looking `emulator-5554` that no longer belongs to anything. The next run on this machine attaches to that stranded device and dies mid-test with `WebDriverError: Request failed with error code ECONNRESET`, which reads as a suite bug rather than an environment one. **The session that killed the run owns the sweep**: `adb -s emulator-5554 emu kill`, then confirm no `qemu*` or `emulator` process and an empty `adb devices`. A healthy run shows the wrapper and the backend as a PAIR with the same start time; a lone backend is the orphan. Learned 2026-09-03 by doing exactly this to a concurrent run in a sibling repo — the instinct to leave another session's process alone is right in general and wrong here.
- **Every Android capture leg on this machine shares one AVD, so two repos cannot capture at once.** With another session live on the same machine, agree the device before booting rather than checking `adb devices` and going: the gap between one run's teardown and the next run's boot reads as "clear" and is not.

## Wait budgets in the integration suites

A whole `evalInObsidian` / `pollInObsidian` closure is evaluated through **one** transport call, and that call is abandoned at about 30 seconds. So the number that matters is the **sum** of the waits a single closure declares, not any one ceiling — and a closure that declares more than the cap cannot report what it was waiting for, because the transport kills it first and reports a bare `script timeout` naming the harness rather than the wait that overran. Every `message:` in such a closure is unreachable by construction.

- **Two treatments, chosen by whether the work is genuinely fast.** Size the ceiling where it is; move the waiting to Node where it is not — a short DOM-reading `pollInObsidian` `poll`, an `until` evaluated in Node, and the long budget in `timeoutInMilliseconds`, which is what both capture suites do.
- **A performance suite buys none of the cap back.** The generous budget such a suite is entitled to is its vitest `testTimeout`; a ceiling declared inside a closure is a promise made to a script that is killed regardless. Reading `desktop-performance` as permission for a 60s in-closure wait is exactly how this repo carried a 120s closure.
- **Lift work that scales with a fixture out of the closure that waits.** `folder-root-scale` writes its 300 notes in a closure of its own, so `NOTE_COUNT` can grow without silently eating the budget the waits were sized against. Writing the notes waits for nothing, so the extra round trip costs the suite nothing.
- **A closure deliberately left under the cap says so**, in a comment opening with the exact line `Under the transport's ~30s per-closure cap, not at it.` and then saying what that budget is made of and why it stays. The rule is silent on an under-cap closure by construction, so without the line there is no way to tell a budget somebody read and kept from one nobody has looked at, and a later sweep at a lower cap re-opens the same decisions. Over a shared module-scope constant the line speaks for the whole file; inside a closure, for that closure alone.
- **Saying it is not the same as clearing it.** A budget under the cap is not a defect, and "read, and left as it is" is a correct outcome — tightening a ceiling to make a number smaller is how a suite starts failing legitimately on a cold machine.

## Deviations from the standard plugin architecture

The workspace convention is that all plugins share the same architecture; intentional deviations are documented here.

- **`demo-vault/Example/` is excluded from `lint:md`** in `scripts/markdownlint-cli2-config.ts`. Those notes are the fixture graph the plugin is demonstrated on, so they exist to carry real wikilinks and embeds — every one of which markdownlint reads as an undefined shortcut reference (MD052). Disable comments inside the fixtures would travel into every exported bundle the demo produces, so the folder is excluded instead. The same notes are excluded from the demo-vault authoring checks, for the same reason.
- **Ships a ZIP dependency (`fflate`)** — no other workspace plugin bundles a compression library. It is reached only from `src/export-targets/zip-export-target.ts`, so the folder-output path stays dependency-free. It needs no `overrides` entry; nothing else in the tree pins it.
  - **It is imported as `fflate/browser`, and the subpath is load-bearing.** `fflate`'s `exports['.']` map lists its `node` condition FIRST, and the shared plugin bundler runs esbuild with `platform: 'node'` — which puts `node` back into the active conditions even though the same config asks for `conditions: ['browser']`. Bare `fflate` therefore bundles `esm/index.mjs`, whose first two lines are `import { createRequire } from 'module'`, and the module body throws `createRequire is not a function` as it loads on a phone. That shipped in 1.0.0 and took the *entire* mobile export path down with it: `mobile-export-destination.ts` statically imports the ZIP target, so the throw happened whether or not ZIP was even turned on, and `invokeAsyncSafely` swallowed it — the dialog closed and nothing else happened, with no error on screen. Nothing here wants the Node build: `zipSync` is synchronous and touches none of the `worker_threads` machinery that build exists to add. **Never shorten the specifier**, and when auditing a new dependency for the same trap, grep the built `dist/build/main.js` for `createRequire` — that is how this one was found.
- **`type-fest` is declared directly**, for the `ReadonlyDeep` view the settings component hands out. Its pre-existing `overrides` entry had to become the self-referencing `"$type-fest"` form: with a literal version there, `npm install type-fest` fails with `EOVERRIDE`. Other plugins in this workspace use the same form for the same reason.
